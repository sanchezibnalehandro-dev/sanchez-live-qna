## 2. Граница продукта и принятая архитектура

Один продукт `sanchez-live-qna`: простой HTML/CSS/JS с ES-модулями; без нового frontend framework, новой базы или второй Q&A-копии.

- `qna_rooms.mode = speaker | panel`. Участники панели используют `qna_speakers`; общий вопрос панели имеет `speaker_id = null`.
- Standalone-комната и multi-session event работают в одном продукте. `event_key` идентифицирует событие, `room.slug` — комнату.
- Гость задаёт Q&A-вопросы без логина. Админ и модератор используют существующий Supabase Auth и принятую модель доверенного аутентифицированного оператора. Новую систему ролей без требования не создавать.
- Выбор комнаты/спикера в Admin — **навигация и редактирование, не эфирная активация**.
- Event room: не более одной текущей Q&A-сессии в одном событии; **ноль допустим**. Неактивная комната не принимает новые вопросы/голоса и не открывает intake. Смена current закрывает intake предыдущей сессии.
- `qna_event_program_items` — существующий **Program v2 compatibility layer**, а не новый универсальный Event Companion. `session` и `service` — разные типы блока. Текущий `service` может означать **ноль текущих Q&A-комнат**. Program cursor и Q&A current marker — разные поля.
- Явные операторские действия `set_current_event_session()` и `set_current_event_program_item()` (а также `clear_current_event_program_item()`) меняют эфирное состояние согласно своему контракту. Нельзя трактовать простое открытие редактора как смену current.
- Гостевой submit и Q&A-голосование используют проверяющие RPC (`submit_guest_question()`, `add_vote()`, `remove_vote()`). Прямой anon INSERT в вопросы/голоса не возвращать, self-vote блокировать; счётчики голосов обновляются атомарно.
- Moderator status/pin mutations room-aware и отклоняют устаревшие запросы после переключения сессии; Realtime игнорирует поздние callbacks и сверяет состояние после подписки. Pending guest actions остаются привязаны к исходной комнате.
- Guest/Moderator `?event=...` следуют текущей Q&A-сессии. Некорректный event и событие без current Q&A **не** переходят неявно на `sanchez-live`.

**Не расширять репозиторий** в People, Meetings, Messaging, общий Event Control Desk или AI/event-platform без нового архитектурного решения. `PRODUCT_DISCOVERY_EVENT_COMPANION.md` остаётся отдельным discovery. Не приписывать автоматическое перераспределение расписания изменению длительности выступления без точной проверки.

### Особые сценарии без новых Q&A-копий

- **ELINA 28:** Audience Choice — отдельное голосование за команды с таблицами `audience_choice_polls` / `audience_choice_votes` и своей страницей, в **том же** Supabase. Действующее решение от 18.10: гость указывает свою команду и выбирает одну **другую**; самоголосование запрещено в UI и backend. Это не `qna_question_votes`; один голос на реального человека между разными устройствами не гарантируется.
